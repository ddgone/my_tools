# 分阶段开发路线图

本文档基于仓库当前真实现状整理后续开发路线。它服务的不是“理想终局”，而是当前已经确定的产品边界：火蜥蜴工具箱是一个个人桌面工具工作台，不以轻量 IDE、工作区平台或重型任务系统作为近期目标。

## 1. 当前判断

截至目前，仓库已经具备以下基础：

- 桌面宿主与单页工作台骨架已完成。
- 本地执行链路已可用，旧 Go/Python 工具通过桥接复用。
- 基础远程执行链路已可用，包含 SSH 连接、远端平台探测、本地构建、上传、执行和日志回传。
- 参数面板、标签页、收藏、最近使用、参数历史、日志导出已接通。
- SSH 连接的新增、编辑、删除、测试基本可用。
- 单工具导出与产物中心已可用，适合继续沿“执行闭环”方向补强。

一句话判断：

当前项目已经足够承担“拿起来就跑工具”的主用途，后续重点应是把远程执行与结果回收做顺手，而不是把产品继续推向更重的 IDE 形态。

## 2. 当前主线

后续工作只围绕以下三条主线展开：

1. 先收口安全、认证和稳定性，保证当前执行主链路可信。
2. 再补远程执行后的结果探测与手动下载，让“执行完之后怎么办”变清楚。
3. 再补参数级远程路径选择与独立 SSH 终端页签，提升远程使用体验。

明确不再作为当前主线的内容：

- 工具工作区模型。
- 通用文件管理器或 FTP/SFTP 客户端。
- 最小编辑器与“保存后重新执行”。
- 重型任务中心、任务命名体系、数据库式历史追踪。
- 继续把产品路线往轻量 IDE 推进。

## 3. 步骤粒度约束

为了避免单步体量过大，后续所有开发步骤统一遵守以下约束：

- 一步最多改 1 个后端主链路模块和 1 个前端消费点。
- 一步最多引入 1 个新的核心数据结构。
- 一步最多新增 1 个对用户可见的新入口。
- 一步的验收必须能在一次本地回归里完成，不依赖后续步骤才能证明价值。
- 如果一步需要同时动执行模型、文件模型、UI 布局三条线，必须拆分。

建议每一步的控制范围：

- Go 后端：约 100 到 300 行净改动为宜。
- Vue 前端：约 50 到 200 行净改动为宜。
- 文档与测试：只补与当前步骤直接相关的部分。

## 4. 阶段一：收口执行主链路

目标：

- 把当前“本地执行 + 远程执行 + SSH 管理”这条主链路先做稳。
- 这一阶段不扩展新形态，只补安全、认证、状态和失败兜底。

### Step 01：修复归档解压安全问题

目的：

- 消除明确的高风险安全问题，避免后续继续在不安全基础上迭代。

范围：

- `tools/go_tools/utm_extract_to_gis/`

改动要点：

- 所有归档内路径在写入前必须做目标目录归一化。
- 拒绝绝对路径、包含 `..` 的路径和越界路径。
- 对链接型条目统一采用保守策略，第一阶段可以直接拒绝处理。

回归方式：

- 构造正常归档，确认功能不退化。
- 构造带路径穿越的恶意归档，确认返回错误且没有越界写文件。

完成标准：

- 正常归档仍能处理。
- 恶意归档无法写出目标目录。

### Step 02：恢复 SSH host key 基本校验

目的：

- 收口远程执行的最基本安全边界。

范围：

- `app/internal/runtime/`
- `app/internal/ssh/`
- 必要时补前端错误提示文案

改动要点：

- 移除执行链路中的 `InsecureIgnoreHostKey()` 依赖。
- 未知主机、首次接受、已知主机匹配、已知主机不匹配要有明确行为。
- 统一“测试连接”和“正式执行”的 host key 校验策略。

回归方式：

- 测试首次连接。
- 测试相同主机指纹匹配。
- 测试指纹变化后拒绝连接。

完成标准：

- 测试连接与正式执行都不再绕过 host key 校验。
- 用户可理解失败原因。

### Step 03：打通 SSH 密钥认证全链路

目的：

- 让 `keyPath` 在保存、测试和正式执行中行为一致。

范围：

- `app/app.go`
- `app/internal/ssh/`
- `app/internal/runtime/`
- `app/frontend/src/components/SSHDetailPanel.vue`

改动要点：

- 统一密码认证和密钥认证的数据模型。
- 统一测试连接与远程执行的认证入口，避免同一认证逻辑写两份。
- 明确表单上密码和密钥的互斥或并存策略。

回归方式：

- 新建连接时使用密码测试和执行。
- 新建连接时使用密钥测试和执行。
- 已保存连接再次编辑后继续测试和执行。

完成标准：

- `keyPath` 不是“表单字段”，而是贯穿后端链路的真实能力。

### Step 04：修复 SSH 新建连接保存后的页签状态

目的：

- 让 SSH 工作区从“勉强可用”变成可持续编辑。

范围：

- `app/frontend/src/stores/workspace.ts`
- `app/frontend/src/components/WorkspaceTabs.vue`
- `app/frontend/src/components/SSHDetailPanel.vue`

改动要点：

- 新建连接保存成功后，当前页签要切换为真实连接实体。
- 避免保存后仍停留在草稿页签，导致误重复创建。
- 统一保存成功后的前端状态更新时机。

回归方式：

- 新建一个 SSH 连接后直接继续编辑、测试、删除。

完成标准：

- 同一页签内完成从“新建草稿”到“已保存连接”的状态切换。

### Step 05：收口任务生命周期和启动期错误兜底

目的：

- 降低执行链路中的隐性脏状态和前端启动崩溃风险。

范围：

- `app/execution.go`
- `app/frontend/src/components/WorkspaceLayout.vue`
- 必要时补 store 侧兜底

改动要点：

- 任务结束后统一清理 `cancel` 状态。
- 启动期 `bootstrap` 或 `hydrate` 出错时，前端不能直接未处理失败。
- 把“失败可见、状态可恢复”作为第一目标，不追求复杂恢复流程。

回归方式：

- 执行完成、执行失败、执行取消三种任务都检查状态清理。
- 模拟启动期接口失败，确认 UI 不白屏。

完成标准：

- 没有脏任务残留。
- 启动失败时有明确提示且界面仍可交互。

### Step 06：提升并发与配置鲁棒性

目的：

- 清理工程性小坑，避免后续结果回收和远程体验被这些基础问题反复绊住。

范围：

- `tools/python_tools/adapter.go`
- `app/app.go`
- `scripts/build.go`

改动要点：

- Python 临时脚本改为唯一文件名或专属临时目录。
- 窗口状态保存不依赖已有完整配置文件。
- 构建脚本对关键错误要显式失败，不再静默吞掉。

回归方式：

- 并发执行同一个 Python 工具。
- 删除或损坏 `app.json` 后再保存窗口状态。
- 在错误目录或关键文件缺失情况下运行构建脚本。

完成标准：

- 并发不互相污染。
- 配置缺失可自恢复。
- 构建脚本失败有明确退出状态。

## 5. 阶段二：补远程结果闭环

目标：

- 让远程执行结束后不只是“看日志”，还能“看到是否有结果可拿”。
- 这一阶段坚持“执行后探测 + 手动下载”，不做自动下载，不做重型任务系统。

### Step 07：定义远程结果探测的最小规则

目的：

- 让宿主知道在远程执行结束后应该去哪里找结果。

范围：

- `libs/core/toolspec/`
- `libs/catalog/builtin/`
- 必要的一个或两个工具 manifest

改动要点：

- 第一层先采用启发式：优先识别 `argKey: output` 以及 `key` 为 `output` / `outputDir` 的路径参数。
- 第二层只给少量启发式不准的工具保留显式覆盖，不要求所有 manifest 一次性重写。
- 明确只支持“显式输出文件或输出目录”的工具，不做自动猜测 stdout 或临时目录。

回归方式：

- 选择至少两个已有工具，验证一个输出目录场景和一个输出文件场景。

完成标准：

- 宿主能稳定判断“这个工具执行后有没有可探测的结果位置”。

### Step 08：实现后端远程结果探测与下载 API

目的：

- 把“能判断有结果”落到“能手动下载”。

范围：

- `app/execution.go`
- `app/internal/runtime/`
- 视情况新增轻量下载模块

改动要点：

- 在远程任务结束后探测输出路径是否存在。
- 对目录结果采用远端打包后下载；对单文件结果直接下载。
- 下载动作由用户手动触发，不在任务成功后自动执行。
- 探测失败、下载失败都作为补充反馈，不反向改写任务成败。

回归方式：

- 成功任务探测到输出目录后手动下载。
- 成功任务探测到单文件后手动下载。
- 失败任务若结果仍存在，也允许手动下载。
- 结果路径不存在时给出明确提示。

完成标准：

- 远程执行页签首次形成“执行 -> 探测 -> 下载结果”的真实闭环。

### Step 09：接通当前工具页签的“下载结果”入口

目的：

- 把结果下载放在最顺手的位置，而不是先做重历史系统。

范围：

- `app/frontend/src/components/ToolDetailPanel.vue`
- `app/frontend/src/stores/execution.ts`
- 必要的当前任务状态扩展

改动要点：

- 当前页签在远程任务结束后显示“下载结果”按钮。
- 按钮只在探测到结果时可用，或允许点击后再提示“未发现结果”。
- 明确区分本次任务的执行状态和下载状态，避免两个流程互相污染。

回归方式：

- 当前远程任务执行成功后直接下载。
- 当前远程任务执行失败但结果存在时仍可下载。

完成标准：

- 常见使用路径不必跳转历史页面，就能完成一次结果回收。

### Step 10：补轻量执行历史中的结果补位

目的：

- 让刚执行过的任务在离开当前页签后，仍有一次补下载的机会。

范围：

- `app/frontend/src/stores/execution.ts`
- 当前最近任务视图或轻量快照消费点

改动要点：

- 历史只保留短期回看所需信息：工具、执行目标、时间、状态、关键日志摘要、是否探测到可下载结果。
- 提供补一次“下载结果”的入口。
- 不引入任务命名、复杂 ID 体系、数据库式任务后台。

回归方式：

- 执行多个远程任务后，从轻量历史补一次下载。

完成标准：

- 历史成为补充入口，而不是新的主工作区。

## 6. 阶段三：补参数级远程路径体验

目标：

- 让远程模式下的路径选择开始具备“执行目标感知”。
- 这一阶段只做参数级体验，不先做独立通用文件管理器。

### Step 11：实现参数级远程路径选择器

目的：

- 让远程模式下点击路径参数的浏览按钮时，看到的是远端目录，而不是本地文件选择器。

范围：

- `app/internal/runtime/` 或新增轻量目录浏览接口
- `app/frontend/src/components/WorkspaceTabs.vue`
- `app/frontend/src/components/ParameterPanel.vue`

改动要点：

- 当前页签处于远程执行目标时，路径参数浏览改走远程路径选择器。
- 当前页签处于本地执行目标时，继续复用本地文件选择器。
- 第一阶段只支持列目录、进入目录、选择文件或目录，不做重命名、删除、批量操作。

回归方式：

- 远程模式下选择输入目录。
- 远程模式下选择输出目录或输出文件。

完成标准：

- 远程模式与本地模式的路径选择终于符合直觉。

### Step 12：把远程/本地路径语义补到少量关键工具

目的：

- 处理启发式不足的少数工具，不为了第一版强推整库重标注。

范围：

- `libs/core/toolspec/`
- 少量 manifest

改动要点：

- 只在必要时补最小语义覆盖，区分远程工作路径和本地接收路径。
- 不要求所有现有参数都重做 schema。
- 保持“约定优先，显式覆盖兜底”的原则。

回归方式：

- 选择至少一个启发式不准的工具，确认路径选择与结果回收行为正确。

完成标准：

- 远程路径体验不再被少量历史清单拖垮。

## 7. 阶段四：补独立 SSH 终端页签

目标：

- 提供一个真正可用的 SSH 终端，但不把它和工具执行深度耦合。

### Step 13：实现独立 SSH 终端页签

目的：

- 给已有 SSH 连接一个直接交互的终端入口。

范围：

- `app/internal/runtime/` 或 SSH 相关后端能力
- `app/frontend/src/components/WorkspaceTabs.vue`
- SSH 列表入口与相关 store

改动要点：

- 基于已保存 SSH 连接打开独立终端页签。
- 第一阶段优先保证可输入、可回显、可复制、可断开重连。
- 不先把工具页签参数、执行状态、结果下载和终端深度绑定。

回归方式：

- 打开 SSH 终端，执行常见命令，断开后重新连接。

完成标准：

- SSH 终端成为独立辅助能力，而不是新的主编排中心。

### Step 14：补少量从连接管理到终端的顺手入口

目的：

- 让 SSH 终端好用，但不把它做成另一套复杂系统。

范围：

- `ToolSidebar.vue`
- SSH 相关表单或列表交互

改动要点：

- 在 SSH 连接列表里增加直接打开终端的入口。
- 必要时在工具页签远程连接区提供“打开终端”捷径，但只做跳转，不共享复杂状态。

回归方式：

- 从 SSH 列表打开终端。
- 从工具页签跳转到对应连接的终端。

完成标准：

- SSH 终端能顺手进入，但仍保持边界清晰。

## 8. 暂缓事项

以下内容现在不建议插队：

- 工具工作区模型与“从本地目录接入工具”。
- 通用远端文件树、双栏传输、完整 FTP/SFTP 客户端。
- 最小文本编辑器与保存后重新执行。
- 重型任务中心、长期历史归档、任务命名与数据库式追踪。
- 工具页签内嵌复杂交互式终端。
- 完整 IDE 级语言服务和代码智能。

这些能力不是没价值，而是都在把产品往更重的方向推，会打断当前“个人桌面工具工作台”的主线。

## 9. 每一步的固定回归模板

每完成一个步骤，至少做以下检查：

```bash
go test ./...
go vet ./...
cd app/frontend && npm run lint
cd app/frontend && npm run typecheck
```

同时增加当前步骤的最小手工回归：

- 安全相关：异常输入、恶意路径、失败提示。
- SSH 相关：密码认证、密钥认证、未知主机、指纹变化。
- 执行相关：成功、失败、取消三条状态流。
- 结果下载相关：结果存在、结果缺失、下载成功、下载失败。
- 路径选择相关：本地模式、本地选择器、远程模式、远程选择器。
- 终端相关：连接、回显、复制、断开与重连。

## 10. 最近可直接开工的前三步

如果立刻开始开发，推荐顺序如下：

1. `Step 02`：恢复 SSH host key 基本校验。
2. `Step 03`：打通 SSH 密钥认证全链路。
3. `Step 08`：实现后端远程结果探测与下载 API。

原因：

- 前两步先把当前远程主链路做稳。
- 第三步开始补“执行后怎么拿结果”，最贴近当前实际使用体验。

这三步做完后，再进入参数级远程路径选择和独立 SSH 终端，会更顺。
