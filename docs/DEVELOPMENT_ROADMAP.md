# 分阶段开发路线图

本文档基于仓库当前真实现状整理后续开发路线，目标不是讨论理想终局，而是给出一条可持续推进、每一步体量受控、能持续交付可见价值的实施顺序。

约束原则：

- 每一步只解决一条明确链路，避免同时改后端模型、前端工作台和文档体系。
- 每一步的目标都必须能被手工验证，优先补最必要的自动化回归。
- 先收口当前主链路上的风险和缺口，再扩展新能力。
- 默认优先 Go 工具工作流；Python 保持降级路径，不作为当前主线阻塞项。
- 如果某一步会引入新的长期接口或目录结构，先在实现里收口，再考虑是否需要新增 ADR。

## 1. 当前基线

截至目前，仓库已经具备以下基础：

- 桌面宿主与单页工作台骨架已完成。
- 本地执行链路已可用，旧 Go/Python 工具通过桥接复用。
- 基础远程执行链路已可用，包含 SSH 连接、远端平台探测、本地构建、上传、执行和日志回传。
- 参数面板、标签页、收藏、最近使用、参数历史、日志导出已接通。
- SSH 连接的新增、编辑、删除、测试基本可用。

当前主要未闭环点：

- SSH 安全边界和密钥认证链路尚未完全收口。
- 任务中心、导出中心仍是占位入口。
- 已有单工具导出，但导出记录、批量导出和导出中心仍未形成统一工作流。
- 尚未形成“工具工作区”模型。
- 没有文件管理器和编辑器，离“轻量 IDE”还差工作区闭环。

一句话判断：

当前项目不是从零开始，而是已经具备“可执行的桌面宿主”，接下来应该把它从“能运行工具”推进到“能围绕工具持续工作”。

## 2. 总体顺序

后续工作分为 5 个阶段：

1. 先收口安全、认证和稳定性，保证执行主链路可信。
2. 再补结果闭环，让工具执行后能明确拿回结果。
3. 然后建立工具工作区模型，为源码接入、编辑和再次执行提供统一对象。
4. 再做文件能力，把远程工作流从“提交参数运行”升级到“同步文件并运行”。
5. 最后补最小编辑器和聚合型页面，让工作台更接近轻量 IDE。

阶段间关系：

- 阶段 1 未完成前，不建议扩展新的远程能力。
- 阶段 2 未完成前，不建议优先做任务中心和导出中心页面。
- 阶段 3 未完成前，不建议上编辑器。
- 阶段 4 未完成前，不建议做复杂交互式终端。

## 3. 步骤粒度约束

为了避免单步体量过大，后续所有开发步骤统一遵守以下约束：

- 一步最多改 1 个后端主链路模块和 1 个前端消费点。
- 一步最多引入 1 个新的核心数据结构。
- 一步最多新增 1 个对用户可见的新入口。
- 一步的验收必须能在一次本地回归里完成，不依赖后续步骤才能证明价值。
- 如果一步需要同时动执行模型、文件模型、UI 布局三条线，必须拆分。

建议每一步的控制范围：

- Go 后端：约 100 到 300 行净改动为宜。
- Vue 前端：约 50 到 200 行净改动为宜。
- 文档与测试：只补与当前步骤直接相关的部分。

## 4. 阶段一：收口执行主链路

目标：

- 把当前“本地执行 + 远程执行 + SSH 管理”这条主链路先做稳。
- 这一阶段不扩展新功能，重点是补安全、认证、状态和失败兜底。

### Step 01：修复归档解压安全问题

目的：

- 消除明确的高风险安全问题，避免后续继续在不安全基础上迭代。

范围：

- `tools/go_tools/utm_extract_to_gis/`

改动要点：

- 所有归档内路径在写入前必须做目标目录归一化。
- 拒绝绝对路径、包含 `..` 的路径和越界路径。
- 对链接型条目统一采用保守策略，第一阶段可以直接拒绝处理。

回归方式：

- 构造正常归档，确认功能不退化。
- 构造带路径穿越的恶意归档，确认返回错误且没有越界写文件。

完成标准：

- 正常归档仍能处理。
- 恶意归档无法写出目标目录。

### Step 02：恢复 SSH host key 基本校验

目的：

- 收口远程执行的最基本安全边界。

范围：

- `app/internal/runtime/`
- `app/internal/ssh/`
- 必要时补前端错误提示文案

改动要点：

- 移除执行链路中的 `InsecureIgnoreHostKey()` 依赖。
- 未知主机、首次接受、已知主机匹配、已知主机不匹配要有明确行为。
- 统一“测试连接”和“正式执行”的 host key 校验策略。

回归方式：

- 测试首次连接。
- 测试相同主机指纹匹配。
- 测试指纹变化后拒绝连接。

完成标准：

- 测试连接与正式执行都不再绕过 host key 校验。
- 用户可理解失败原因。

### Step 03：打通 SSH 密钥认证全链路

目的：

- 让 `keyPath` 在保存、测试和正式执行中行为一致。

范围：

- `app/app.go`
- `app/internal/ssh/`
- `app/internal/runtime/`
- `app/frontend/src/components/SSHDetailPanel.vue`

改动要点：

- 统一密码认证和密钥认证的数据模型。
- 统一测试连接与远程执行的认证入口，避免同一认证逻辑写两份。
- 明确表单上密码和密钥的互斥或并存策略。

回归方式：

- 新建连接时使用密码测试和执行。
- 新建连接时使用密钥测试和执行。
- 已保存连接再次编辑后继续测试和执行。

完成标准：

- `keyPath` 不是“表单字段”，而是贯穿后端链路的真实能力。

### Step 04：修复 SSH 新建连接保存后的页签状态

目的：

- 让 SSH 工作区从“勉强可用”变成可持续编辑。

范围：

- `app/frontend/src/stores/workspace.ts`
- `app/frontend/src/components/WorkspaceTabs.vue`
- `app/frontend/src/components/SSHDetailPanel.vue`

改动要点：

- 新建连接保存成功后，当前页签要切换为真实连接实体。
- 避免保存后仍停留在草稿页签，导致误重复创建。
- 统一保存成功后的前端状态更新时机。

回归方式：

- 新建一个 SSH 连接后直接继续编辑、测试、删除。

完成标准：

- 同一页签内完成从“新建草稿”到“已保存连接”的状态切换。

### Step 05：收口任务生命周期和启动期错误兜底

目的：

- 降低执行链路中的隐性脏状态和前端启动崩溃风险。

范围：

- `app/execution.go`
- `app/frontend/src/components/WorkspaceLayout.vue`
- 必要时补 store 侧兜底

改动要点：

- 任务结束后统一清理 `cancel` 状态。
- 启动期 `bootstrap` 或 `hydrate` 出错时，前端不能直接未处理失败。
- 把“失败可见、状态可恢复”作为第一目标，不追求复杂恢复流程。

回归方式：

- 执行完成、执行失败、执行取消三种任务都检查状态清理。
- 模拟启动期接口失败，确认 UI 不白屏。

完成标准：

- 没有脏任务残留。
- 启动失败时有明确提示且界面仍可交互。

### Step 06：提升并发与配置鲁棒性

目的：

- 清理工程性小坑，避免后续工作区能力被这些基础问题反复绊住。

范围：

- `tools/python_tools/adapter.go`
- `app/app.go`
- `scripts/build.go`

改动要点：

- Python 临时脚本改为唯一文件名或专属临时目录。
- 窗口状态保存不依赖已有完整配置文件。
- 构建脚本对关键错误要显式失败，不再静默吞掉。

回归方式：

- 并发执行同一个 Python 工具。
- 删除或损坏 `app.json` 后再保存窗口状态。
- 在错误目录或关键文件缺失情况下运行构建脚本。

完成标准：

- 并发不互相污染。
- 配置缺失可自恢复。
- 构建脚本失败有明确退出状态。

## 5. 阶段二：补结果与导出工作流闭环

目标：

- 让工具运行结束后不只是“看日志”，还能“拿结果”。
- 这一阶段优先做最小闭环，不先做完整的导出中心。

### Step 07：定义最小产物契约（已完成）

目的：

- 让宿主知道“什么算结果”，而不是只知道“任务结束了”。

范围：

- `libs/core/toolspec/`
- `libs/catalog/builtin/`
- 必要的一个或两个工具 manifest

改动要点：

- 在现有 `export` 规格基础上，收敛一个最小可用模型。
- 第一阶段只支持最简单的产物描述：
  - 单输出文件
  - 固定输出目录
  - 基于 glob 的输出匹配
- 不做复杂的后处理、压缩、重命名流水线。

回归方式：

- 选择一个已有 Go 工具，为它声明一个明确输出路径或匹配规则。

完成标准：

- 有至少一个真实工具能被规格声明为“有产物”。

### Step 08：实现后端产物收集与导出 API（已完成）

目的：

- 把“规格声明”落到“实际可下载”。

范围：

- `app/execution.go`
- `app/dialog.go`
- 可能新增一个小型 `app/internal/export/` 或直接先收口在现有模块

改动要点：

- 任务完成后，根据工具规格定位产物。
- 提供“选择导出位置并复制产物”的 API。
- 第一阶段只支持单个产物或同一目录内的一组简单产物。

回归方式：

- 成功执行后手动点击导出，确认能拿到文件。
- 产物缺失时给出明确错误。

完成标准：

- 导出不再只是日志导出，至少有一个真实工具支持结果文件导出。

### Step 09：接通工具详情页的一键导出（已完成）

目的：

- 把后端能力接到现有工作台，而不是继续停留在禁用按钮。

范围：

- `app/frontend/src/components/ToolDetailPanel.vue`
- `app/frontend/src/stores/execution.ts`

改动要点：

- 启用当前已占位的“导出”按钮。
- 根据任务状态和工具规格控制按钮可用性。
- 导出过程中给用户明确反馈。

回归方式：

- 成功任务可导出。
- 失败任务或无产物任务按钮不可用或提示原因。

完成标准：

- 现有工具详情页形成“执行 -> 导出”的最小闭环。

### Step 10：实现最小导出记录与导出中心

目的：

- 把当前“单次导出成功就结束”的能力升级为“可回看、可重复操作”的工作流。

范围：

- `app/export.go`
- `app/internal/runtimeenv/`
- 前端导出相关 store
- `app/frontend/src/components/ActivityBar.vue`
- 新增或接通导出中心视图

改动要点：

- 记录最近导出动作、来源工具、导出模式、目标平台、目标路径和结果状态。
- 让活动栏里的导出中心从占位入口变成真实页面。
- 提供最小的“重新打开目录 / 再次导出 / 查看最近结果”能力。

回归方式：

- 连续导出多个工具后，在导出中心看到记录。
- 关闭应用再打开，确认最近导出记录仍可回看或明确采用不持久化策略。
- 从导出中心再次打开目录或触发二次导出。

完成标准：

- 单工具导出不再只是一次性动作，而是有最小可追踪的工作流。

## 6. 阶段三：建立工具工作区模型

目标：

- 把“工具”从静态目录项升级为“可持续工作的对象”。
- 这一阶段只建立模型和基础入口，不立即做编辑器。

### Step 11：定义工作区对象

目的：

- 为源码目录、入口文件、默认参数、远程目标、输出位置提供统一落点。

范围：

- `app/frontend/src/types/`
- `app/frontend/src/stores/workspace.ts`
- 后端如需持久化，再补最小读写接口

改动要点：

- 区分“工具清单实体”和“工具工作区实例”。
- 工作区至少包含：
  - 工具 ID 或来源标识
  - 本地源码目录
  - 入口文件
  - 默认运行参数
  - 最近远程目标
  - 输出目录或产物策略覆盖
- 第一阶段可以先保存在前端本地状态。

回归方式：

- 创建一个工作区对象并刷新后保持。

完成标准：

- 工作区成为后续文件树、编辑器、再次执行的统一载体。

### Step 12：新增“从本地目录接入工具”的最小入口

目的：

- 让工作区不再只依赖当前内置工具清单。

范围：

- 后端文件选择 API 复用
- `WorkspaceTabs.vue`
- 侧栏或工具详情页上新增最小入口

改动要点：

- 用户可以选择一个本地目录作为工作区根目录。
- 第一阶段不做复杂自动识别，只要求用户填写最少元数据。
- 先把“能接入”跑通，再考虑目录扫描和模板初始化。

回归方式：

- 接入一个本地 Go 工具目录，保存后能作为工作区打开。

完成标准：

- 宿主开始具备“接入用户自己写的工具”的能力。

### Step 13：让远程执行支持工作区来源

目的：

- 把当前“跑内置工具”推进到“跑工作区工具”。

范围：

- `app/execution.go`
- `app/internal/builder/`
- 必要的工作区模型读写

改动要点：

- 远程执行时不再只依赖清单里的静态 `source.entry`。
- 支持从工作区对象中解析源码根目录和入口信息。
- 第一阶段只保证 Go 工具能从工作区构建后远程执行。

回归方式：

- 接入一个本地 Go 工具目录后，直接远程执行。

完成标准：

- 工作区不是只可展示，而是真能驱动远程执行。

## 7. 阶段四：补文件能力

目标：

- 先让“文件同步”和“结果回收”变顺，再考虑复杂终端和编辑器增强。

### Step 14：补最小远端文件浏览能力

目的：

- 让远程执行结果和远端目录不再完全黑盒。

范围：

- `app/internal/runtime/` 或新增轻量文件接口
- 前端新增一个简单远端目录面板

改动要点：

- 第一阶段只支持：
  - 列目录
  - 查看文件元信息
  - 下载文件
- 不先做重命名、移动、删除、批量操作。

回归方式：

- 浏览远端工作目录。
- 下载一个远端输出文件到本地。

完成标准：

- 用户可以从工作台确认远端输出目录里到底生成了什么。

### Step 15：补本地到远端的最小上传能力

目的：

- 为后续编辑后快速同步和手工上传辅助文件打底。

范围：

- 复用现有 SSH 上传基础
- 前端文件面板或工作区入口增加上传动作

改动要点：

- 第一阶段只支持“上传单文件到指定目录”。
- 不做目录镜像、增量同步、冲突合并。

回归方式：

- 上传一个配置文件或辅助数据文件到远端并确认存在。

完成标准：

- 工作台首次具备主动管理远端文件的能力。

### Step 16：把产物下载和远端文件下载统一体验

目的：

- 避免“导出”和“下载”做成两套孤立交互。

范围：

- `ToolDetailPanel.vue`
- 远端文件面板
- 可能的导出 store

改动要点：

- 统一下载位置选择和成功反馈。
- 区分“任务产物下载”和“任意远端文件下载”，但共用基础操作。

回归方式：

- 从工具导出下载。
- 从远端文件面板下载。

完成标准：

- 下载操作不再分裂成多套风格。

## 8. 阶段五：补最小编辑与聚合页面

目标：

- 这一阶段才开始向“轻量 IDE”靠近，但仍坚持最小功能优先。

### Step 17：接入最小文本编辑器

目的：

- 形成“打开文件 -> 编辑 -> 保存”的最短回路。

范围：

- 前端编辑器组件
- 工作区 tab 模型
- 后端文件读写 API

改动要点：

- 第一阶段只支持文本文件。
- 先不做复杂语言服务、诊断、补全、diff。
- 编辑器能力以“稳定读写”和“脏状态提示”为主。

回归方式：

- 打开工作区文件，修改内容，保存成功，再次打开确认。

完成标准：

- 工作台第一次拥有真实编辑能力。

### Step 18：接通“保存后重新执行”

目的：

- 把编辑能力和当前执行主链路真正连起来。

范围：

- 编辑器组件
- 工作区 store
- 执行 store

改动要点：

- 当前工作区保存后可一键重新执行。
- 默认沿用上次参数和上次远程目标。
- 第一阶段先不做自动保存和自动执行。

回归方式：

- 修改 Go 工具代码，保存后直接本地执行。
- 修改 Go 工具代码，保存后直接远程执行。

完成标准：

- 形成“改代码 -> 保存 -> 再执行”的可见闭环。

### Step 19：实现最小任务中心

目的：

- 把当前已经存在的任务状态，从分散在各 tab 中提升为统一视图。

范围：

- `ActivityBar.vue`
- 新增任务中心页面
- `execution.ts`

改动要点：

- 展示当前任务列表、状态、目标、开始时间、结束时间。
- 支持跳回对应工具 tab。
- 第一阶段不做复杂筛选和历史归档。

回归方式：

- 同时运行多个任务并在任务中心查看。

完成标准：

- 任务中心不再是禁用入口。

### Step 20：增强导出中心与批量导出

目的：

- 在最小导出中心已经接通后，继续补批量导出和导出结果管理。

范围：

- `ActivityBar.vue`
- 新增导出中心页面
- 导出相关 store

改动要点：

- 在现有导出记录基础上补批量操作。
- 支持按工具、模式、状态筛选最近导出结果。
- 提供批量再次导出、批量打开目录或清理历史的最小能力。

回归方式：

- 连续导出多个结果文件并在页面里查看。
- 选择多条导出记录执行批量操作。

完成标准：

- 导出中心开始承担真实的导出管理职责，而不只是记录列表。

## 9. 暂缓事项

以下内容现在不建议插队：

- Python 远端零依赖 runtime 托管。
- Go 工具链托管下载。
- 团队内部工具分发体系。
- 多平台预编译产物矩阵。
- 复杂交互式 shell 终端。
- 完整 IDE 级语言服务和代码智能。

这些能力不是没价值，而是当前都会打断“先收口主闭环”的节奏。

## 10. 每一步的固定回归模板

每完成一个步骤，至少做以下检查：

```bash
go test ./...
go vet ./...
cd app/frontend && npm run lint
cd app/frontend && npm run typecheck
```

同时增加当前步骤的最小手工回归：

- 安全相关：异常输入、恶意路径、失败提示。
- SSH 相关：密码认证、密钥认证、未知主机、指纹变化。
- 执行相关：成功、失败、取消三条状态流。
- 文件相关：上传、下载、产物缺失、目标路径不存在。
- 编辑相关：脏状态、保存成功、保存失败、重新执行。

## 11. 推荐执行节奏

为了避免路线图写得太大、实现时失控，建议按以下节奏推进：

- 一次只做 1 个步骤，不合并相邻步骤。
- 每个步骤先改代码，再补最小测试，最后修文档。
- 每完成 2 到 3 个步骤，回头审一次是否需要微调路线，而不是一路硬冲到底。
- 如果中途发现某一步需要跨越多个阶段，优先回退并拆小，不在原步骤上继续堆复杂度。

## 12. 最近可直接开工的前三步

如果立刻开始开发，推荐顺序如下：

1. `Step 02`：恢复 SSH host key 基本校验。
2. `Step 03`：打通 SSH 密钥认证全链路。
3. `Step 08`：实现后端产物收集与导出 API。

原因：

- 前两步先把当前远程主链路做稳。
- 第三步开始补结果闭环，能最快提升“工具工作流”的完成度。

这三步做完后，再进入工作区模型，会更顺。
