# Python 环境使用说明

本文档只说明当前已经落地的 Python 环境能力，以及它在桌面宿主中的真实影响范围。

## 1. 先说结论

- Python 工具的本地执行依赖一份由宿主管理的 Python 工具环境。
- 当前这套 Python 环境能力只管理三件事：
  - 选择一个本地 Python 3 作为基础解释器
  - 在 `toolchains/` 下按基础 Python 隔离创建托管虚拟环境
  - 按内置 Python 工具脚本的动态扫描结果一键安装第三方包
- 当前暂时不包含：
  - 托管 Python 下载
  - conda / poetry / uv 等额外环境管理

## 2. 为什么 Python 和 Go 不一样

- Go 工具的本地执行直接复用宿主编译时桥接进来的运行闭包。
- Python 工具的本地执行会统一调用宿主管理的托管虚拟环境去执行脚本。
- 所以：
  - Go 未配置时，本地运行通常不受影响
  - Python 未配置时，Python 工具的本地运行会直接受影响

如果你看到状态栏写着 `Python 未配置 · 本地运行受影响`，意思就是：

- Python 工具的本地执行当前不可用
- 需要先在系统首选项里选择一个基础 Python，并准备托管工具环境

## 3. 用户能做什么

当前系统首选项里的 Python 页签支持四类操作：

### 3.1 选择基础 Python

- 选择机器上已经安装好的 Python 3 可执行文件
- 宿主会优先推荐 PATH 中可用的 `python3`
- 也会自动识别 `python3.12` 这类命令入口
- 如果 `python` 实际是 Python 2，则不会被当成可用基础解释器

### 3.2 创建或重建工具环境

- 宿主会使用当前基础 Python 在 `toolchains/` 下创建托管虚拟环境
- 每个基础 Python 都有自己独立的一套托管工具环境，可以长期共存
- 当基础 Python 变化时，会自动切换到对应环境；若该环境不存在，再提示创建
- 本地 Python 工具真正运行时，只使用这份托管虚拟环境，不直接污染用户自己的 Python 环境

### 3.3 选择 `<无 Python>`

- 这不是“检测失败”，而是用户主动清除当前 Python 环境
- 进入这个状态后：
  - Python 工具的本地执行会被阻断
  - 宿主不会继续使用现有托管虚拟环境
  - 宿主不会自动回退到 PATH 或已发现的 Python

### 3.4 一键安装依赖

- 宿主会读取内置 Python 工具 manifest，并扫描对应脚本里的 `import` / `from ... import ...`
- 然后使用托管虚拟环境里的 Python 执行：

```text
python -m pip install ...
```

- 安装成功后，Python 状态会自动刷新
- 创建环境和安装依赖现在都会显示任务级进度
- 运行中的任务可以停止；再次点击对应按钮时，会按当前状态继续重试

## 4. 依赖现在怎么维护

- 当前不再手写维护 `python_requirements.json` 这一类宿主依赖清单文件。
- 宿主会直接根据内置 Python 工具脚本里的导入语句，动态计算需要安装和检查的第三方包。
- 当前规则是：
  - 忽略标准库模块，标准库列表来自 `pipreqs` 的 `stdlib` 数据
  - 默认把导入根模块同时当作包名与模块名，例如 `numpy`、`pyproj`
  - 对“导入名 != pip 包名”的场景，优先使用 `pipreqs` 的映射数据，例如 `PIL -> Pillow`、`bs4 -> beautifulsoup4`、`yaml -> PyYAML`
  - 然后统一在托管虚拟环境里检查和安装这些包

### 4.1 这两份数据文件放在哪里

- 当前正式资源文件位于：
  - `app/internal/toolchain/pythondata/mapping.txt`
  - `app/internal/toolchain/pythondata/stdlib.txt`
- 宿主会通过 `go:embed` 把它们打进桌面程序，因此运行时不依赖额外下载，也不依赖用户机器上安装 `pipreqs`。

### 4.2 这两份文件分别做什么

- `mapping.txt`
  - 处理“导入名和 pip 包名不一致”的情况。
  - 例如脚本里写 `from PIL import Image`，安装时应落到 `Pillow`，而不是错误地执行 `pip install PIL`。
- `stdlib.txt`
  - 标记哪些模块属于 Python 标准库。
  - 这些模块在动态扫描时会被直接忽略，避免把 `json`、`pathlib`、`argparse` 之类误判成第三方依赖。

### 4.3 这两份文件来自哪里

- 当前这两份文件来源于 `pipreqs` 项目使用的数据文件。
- 采用这套数据的原因是：
  - 它已经覆盖了大量常见的导入名与包名映射
  - 它已经整理了可直接复用的标准库模块集合
  - 比宿主自己长期手写维护一份小映射表更可靠，也更省心

### 4.4 后续怎么维护

- 建议定期更新这两份文件，尤其是在以下情况之后：
  - 新接入了一批 Python 工具
  - 遇到了新的“导入名 != pip 包名”场景
  - 升级了项目常用的 Python 大版本
  - 发现标准库识别或第三方包识别有误判
- 实际维护策略建议保持简单：
  - 优先直接从 `pipreqs` 同步最新 `mapping.txt` 与 `stdlib.txt`
  - 然后替换 `app/internal/toolchain/pythondata/` 下的正式文件
  - 最后运行一次 `go test ./...` 和 `go run scripts/build.go` 做回归确认
- 这样做的好处是：
  - Go 宿主仍然掌控 Python 依赖解析流程
  - 依赖扫描规则有稳定的内置资源，不受运行时环境影响
  - Python 侧又能借用成熟社区数据，而不是重复造轮子

截至当前版本，动态扫描到的第三方包至少包括：

- `open3d`
- `laspy`
- `numpy`
- `mgrs`
- `pyproj`
- `requests`

这些包当前主要服务于 `restore_pcd_by_mgrs` 与 `python_env_diagnostics` 这两个 Python 工具。

## 5. 状态栏怎么看

底部状态栏里的 Python 状态块是当前唯一的轻量环境入口。

### 已就绪

- 显示类似：

```text
Python 已就绪 · Python 3.11.9
```

- 点击可以打开 Python 设置页
- hover 会显示：
  - 当前基础 Python
  - 托管工具环境的实际路径
  - pip 与动态扫描依赖是否已就绪

### 未配置

- 显示类似：

```text
Python 未配置 · 本地运行受影响
```

- 点击可以直接打开 Python 设置页
- hover 会明确说明：
  - Python 工具的本地运行需要 Python + pip

### 工具环境未创建

- 显示类似：

```text
Python 工具环境未创建 · 点击处理
```

- 说明已经找到基础 Python，但托管虚拟环境还没创建或需要重建

### 正在创建环境 / 正在安装依赖

- 设置页会显示任务卡片、阶段文案、当前包名和进度条
- 可以直接停止当前任务
- 停止或失败后，再次点击按钮会按当前状态继续处理

### 依赖未就绪

- 显示类似：

```text
Python 依赖未就绪 · 点击安装
```

- 说明已经找到 Python，但还没有完成依赖安装

## 6. 常见使用场景

### 想本地运行 Python 工具

- 先选择一个基础 Python
- 再创建托管工具环境
- 然后在设置页里一键安装依赖
- 如果你想确认当前到底用了哪套 Python，可以直接运行 `python_env_diagnostics`

### 只想先清掉 Python 环境

- 可以选择 `<无 Python>`
- 这适合验证“没有 Python 环境时，本地运行应该怎样提示”

### 机器上已经有 Python

- 优先直接选择本地 Python
- 宿主会把它加入候选列表，后续可重复切换

## 7. 排障建议

### 已经选了 Python，但仍提示未配置

- 先检查是否误选了 `<无 Python>`
- 再检查设置页里当前是否真的选中了某个基础 Python
- 如果基础 Python 已经变更，再重建一次工具环境

### 已经选了 Python，但提示缺少 pip

- 说明当前托管工具环境里的 pip 不可用
- 优先点击“重建工具环境”
- 如果仍失败，再重新选择一个带 `venv` 的 Python 3

### 一键安装依赖失败

- 当前实现会先确保托管虚拟环境存在，再在其中执行 `pip install`
- 如果基础 Python 缺少 `venv`，或网络环境受限，安装会失败
- 这时优先改选一个带 `venv` 的 Python 3，或处理网络代理问题

### 动态扫描会不会完全替代人工维护

- 当前实现已经把动态扫描结果作为依赖检查与一键安装的真实来源。
- 这意味着接入普通 Python 工具时，通常不再需要额外手写依赖清单。
- 但它仍有边界：
  - 如果遇到 `pipreqs` 数据里也没有覆盖的“包名和导入名不同”场景，仍然需要继续补映射来源
  - 如果依赖来自动态导入、插件系统或运行时拼接字符串，扫描可能无法覆盖
  - 如果脚本使用了仓库内本地模块，而不是第三方包，应该避免误写成外部依赖

## 8. 验收清单

如果你要验证这套能力是否正常，最小检查清单如下：

- 选择基础 Python 后，设置页会自动创建或更新托管工具环境
- `python` 为 Python 2 时不会被错误当成可用基础解释器
- `python3` 或 `python3.12` 这类入口都能被自动识别
- 切换不同基础 Python 时，对应托管虚拟环境可以共存并复用
- 依赖未安装时，设置页能列出缺失包并可一键安装
- 依赖列表来自内置 Python 脚本的动态扫描，而不是手写 JSON 清单
- 创建环境与安装依赖时，设置页会显示可停止的进度任务
- 依赖安装完成后，状态栏显示 `Python 已就绪`
- 选择 `<无 Python>` 后，Python 工具的本地执行会被阻断并引导去配置
