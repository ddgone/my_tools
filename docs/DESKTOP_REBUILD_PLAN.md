# 火蜥蜴工具箱桌面化重构方案

> **注意：本文档中的路径引用已过时。当前项目结构见 [README.md](../README.md)**

本文档定义从当前 `tview` 工具箱重构到桌面工具平台的完整方案。目标不是把旧界面搬到桌面上，而是建立一个以桌面宿主为入口、可本地执行、可远程执行、可导出单工具产物的平台。

## 1. 已确认的方向

- 桌面宿主优先，导出能力作为第二阶段核心能力。
- 技术底座采用 `Wails + Vue 3 + TypeScript`。
- 保持单仓库，但在仓库内建立强模块边界。
- 旧 `Tool` 接口彻底退役，使用新的统一工具规格。
- Python 工具默认以脚本源码交付。
- 内置工具由平台管理；用户修改通过“复制为自定义工具”实现。
- 第一阶段不追求旧 TUI 交互原样保留，只追求能力迁移。
- 第一阶段 MVP 只打通一条主路径闭环。
- 参数输入采用“结构化表单默认 + 原始参数模式兜底”。

## 2. 产品目标

### 2.1 第一阶段目标

打通一条可用的主路径：

1. 选择一个工具
2. 填写参数
3. 本地执行
4. 查看日志结果
5. 切换到远程执行
6. 为目标平台生成工具专属产物
7. 上传到远端
8. 执行并回传日志
9. 清理远端临时产物
10. 导出该工具

### 2.2 第二阶段目标

- 扩展工具目录、搜索、收藏、历史、设置、任务中心
- 完善自定义工具工作区
- 丰富导出类型与批量导出
- 增强 SSH 连接管理与凭据体验

## 3. 非目标

- 不保留旧 `tview` 页面结构和快捷键设计
- 不追求第一阶段就覆盖所有旧功能
- 不做长期驻留远端代理
- 不把 Python 工具优先打成二进制
- 不在第一阶段开放原地修改内置工具

## 4. 推荐技术栈

### 4.1 桌面宿主

- `Wails`
- `Vue 3`
- `TypeScript`
- `Vite`

### 4.2 前端 UI

- `Naive UI` 作为成熟组件库
- `Tailwind CSS` 负责布局、间距、视觉细节和快速样式拼装
- `Pinia` 管理前端状态
- `Vue Router` 管理桌面宿主内部页面

说明：

- 之所以不用 `shadcn-vue` 作为首选，是因为第一阶段目标是快速落地成熟桌面宿主，`Naive UI` 更适合直接承接表单、树、日志面板、抽屉、标签页、通知和配置页。
- 之所以仍保留 `Tailwind CSS`，是为了满足界面定制效率和后续美化空间。

## 5. 单仓库模块边界

推荐目录：

```text
/
├─ app/
│  └─ desktop/                  # Wails 桌面宿主
├─ frontend/
│  └─ desktop/                  # Vue 3 前端
├─ core/
│  ├─ toolspec/                 # 工具规格、参数模型、校验
│  ├─ execution/                # 执行请求、日志事件、任务状态
│  ├─ export/                   # 导出请求与产物描述
│  └─ connection/               # SSH 连接模型
├─ runtime/
│  ├─ local/                    # 本地执行
│  ├─ remote/                   # SSH 上传、执行、清理
│  ├─ stream/                   # 日志流与取消
│  └─ cache/                    # 构建缓存、产物缓存
├─ builder/
│  ├─ go/                       # Go 工具单工具构建
│  ├─ python/                   # Python 脚本产物整理
│  └─ packaging/                # 导出产物打包
├─ catalog/
│  ├─ builtin/                  # 内置工具加载
│  ├─ custom/                   # 自定义工具工作区
│  └─ manifests/                # 工具清单加载和索引
├─ toolkits/
│  ├─ go/
│  └─ python/
├─ docs/
└─ scripts/
```

边界原则：

- `app/desktop` 只做桌面宿主绑定，不承载业务规则。
- `frontend/desktop` 只关心界面和交互，不自行解释工具执行规则。
- `core` 只定义平台语言和模型，不直接碰 SSH、文件系统和构建命令。
- `runtime` 负责编排执行过程，不定义工具内容。
- `builder` 只关注如何得到工具专属产物。
- `catalog` 负责“有哪些工具”和“工具来自哪里”。

## 6. 新的工具模型

## 6.1 基本原则

每个工具都由两部分组成：

- `工具清单`：静态描述
- `工具适配器`：实际运行逻辑

## 6.2 为什么必须清单优先

- 桌面宿主需要在不执行工具代码的情况下渲染目录和表单
- 平台需要支持复制为自定义工具
- 导出与远程执行都需要读取静态策略
- Python 工具天然适合文件化管理

## 6.3 推荐清单格式

第一阶段采用：

- `YAML` 作为工具清单格式
- `JSON Schema` 作为清单校验规范

原因：

- `YAML` 对人工编辑更友好，适合未来自定义工具
- `JSON Schema` 便于 Go 与 TypeScript 两端共享校验规则

## 6.4 工具清单建议字段

```yaml
id: restore_pcd_by_mgrs
name: 白犀牛偏转后的pcd文件转换回未偏转的las文件
kind: python
category: 点云处理
icon: cloud
description: 根据文件名中的 MGRS 信息恢复 UTM 坐标
docs:
  usage: docs/usage.md
params:
  - key: input
    type: path
    label: 输入目录
    required: true
  - key: output
    type: path
    label: 输出目录
  - key: workers
    type: number
    label: 并发数
execution:
  local:
    adapter: python-script
  remote:
    strategy: upload-script-and-run
export:
  strategy: export-script
source:
  entry: script.py
```

## 7. Go 工具与 Python 工具的交付策略

### 7.1 Go 工具

- 本地执行、远程执行、导出都尽量复用同一个“单工具构建产物”
- 首次执行前由 `builder/go` 生成目标平台对应产物并写入本地缓存
- 后续本地执行、远程执行和导出都优先复用缓存
- 远程执行完成后仅清理远端临时目录，不清理本地缓存
- 开发阶段使用仓库内的“开发态运行时目录”承载缓存、脚本副本、日志和导出内容，其目录形态尽量镜像安装态运行时目录

推荐实现：

- 每个 Go 工具放在 `toolkits/go/<tool-id>/`
- 工具逻辑实现统一 Runner 接口
- `builder/go` 在缓存目录生成临时 wrapper `main.go`
- 该 wrapper 只引入目标工具 Runner 与共享运行时
- 执行 `go build` 生成单工具二进制

这样可以避免把整个工具箱再次编进单工具产物。

### 7.2 Python 工具

- 安装目录内直接放置完整脚本
- 本地执行直接调用脚本
- 远程执行直接上传脚本及必要伴随文件
- 导出直接导出脚本及最小运行说明

第一阶段默认不做：

- PyInstaller
- Nuitka
- Python 单文件二进制打包

## 8. 本地、远程、导出的统一链路

### 8.1 本地执行

- 前端提交工具 ID、参数、执行目标
- 后端根据工具清单解析参数
- Go 工具走“取缓存或构建产物 -> 执行产物”
- Python 工具走“定位脚本 -> 调用解释器执行”
- 日志以事件流回传前端

### 8.2 远程执行

- 用户选择 SSH 连接
- 平台根据远端 OS/Arch 判断所需产物
- Go 工具：
  - 取本地缓存或触发编译
  - 上传工具专属产物到远端临时目录
  - 执行
  - 拉回日志
  - 清理远端临时文件
- Python 工具：
  - 上传脚本与伴随文件
  - 调用远端 Python 执行
  - 拉回日志
  - 清理远端临时文件

### 8.3 导出

- Go 工具：直接导出单工具二进制，附带最小说明文件
- Python 工具：直接导出脚本、伴随资源和最小说明文件
- 第二阶段再考虑导出模板、批量导出和压缩包形式

## 9. 第一阶段界面布局（单页工作台范式）

采用 IDE/Postman 风格的单页工作台，不再使用路由跳转的多页面模式。

### 9.1 全局布局

```
┌─────────────────────────────────────────────────────────┐
│ HEADER: Logo + 应用标题 | 全局搜索 | SSH/导出/任务/设置  │
├────────────┬────────────────────────────────────────────┤
│ SIDEBAR    │ TAB BAR: [工具页签1] [工具页签2] [+]       │
│ 256px      ├────────────────────────────────────────────┤
│            │ TOOL HEADER                                │
│ [搜索框]   │ 工具名称 + 说明 + 运行/远程/导出操作按钮      │
│            ├────────────────────────────────────────────┤
│ 分类A      │ PARAMETER TABS                             │
│  ├ 工具1   │ [可视化表单 | 命令行模式 | 工具说明]          │
│  ├ 工具2   │                                            │
│  └ 工具3   │ [参数配置区域...]                           │
│ 分类B      ├────────────────────────────────────────────┤
│  └ 工具4   │ TERMINAL (始终可见)                         │
│            │ [清空] [复制] [导出日志]                     │
│ 底部导航   │                                            │
│ 工具|SSH   │ [实时日志输出...]                            │
│ |历史|导出 │                                            │
├────────────┴────────────────────────────────────────────┤
│ FOOTER: ● 就绪 | Go版本 | Python版本 | 应用版本          │
└─────────────────────────────────────────────────────────┘
```

### 9.2 核心交互原则

- **侧边栏常驻**：工具分类树始终在左侧，点击工具即在工作区打开/切换到对应页签
- **多页签**：主工作区支持同时打开多个工具，以页签形式排列，切换时保留各自的参数输入和输出状态
- **上下分栏**：上半部分为工具说明 + 参数配置区，下半部分为始终可见的执行终端
- **切换工具不打断任务**：切换页签时后台任务继续运行，侧边栏和页签显示运行状态指示
- **远程执行占位**：远程执行按钮和配置区保留 UI 位置，标记为"即将推出"

### 9.3 侧边栏内容

- 顶部：工具搜索输入框（实时过滤）
- 主体：按 category 分组的工具分类树
  - 分类标题可折叠
  - 工具项显示名称 + 类型标签（go/python）
  - 正在运行的工具显示状态指示（绿点/旋转动画）
- 底部：视图切换按钮组（工具列表 / SSH 服务器 / 任务历史 / 导出中心）

### 9.4 参数配置区

- 默认显示"可视化表单"模式（结构化表单）
- 可切换至"命令行模式"（原始参数字符串输入）
- 第三个 tab："工具说明"（usage 文档）
- Python 工具显示"Python 解释器路径"输入
- 参数预览区实时显示生成的 CLI 参数字符串

### 9.5 执行终端

- 始终可见的底部面板
- 支持清空、复制日志、导出日志
- 实时流式输出，自动滚动到底部
- 未执行时显示占位提示文字

## 10. 第一阶段视图组件

单页工作台内部不设路由页面，改为组件化架构：

- `App.vue` → `WorkspaceLayout.vue`（全局布局壳）
  - `AppHeader.vue`（顶部导航栏）
  - `ToolSidebar.vue`（左侧工具树）
  - `WorkspaceTabs.vue`（工具页签栏 + 主工作区）
    - `ToolDetailPanel.vue`（工具详情 + 操作按钮）
    - `ParameterPanel.vue`（参数配置区，含三种模式切换）
    - `ExecutionTerminal.vue`（执行终端）
  - `StatusBar.vue`（底部状态栏）

不再需要的旧页面：

- ~~`HomeView.vue`~~（其功能被 `ToolSidebar` + `ToolDetailPanel` 替代）
- ~~`ExecuteView.vue`~~（其功能被 `WorkspaceTabs` 内的各面板替代）
- ~~`Vue Router`~~（不再需要路由）

## 11. 状态与日志模型

每次执行都产生一个任务对象，至少包含：

- `taskId`
- `toolId`
- `targetType`
- `targetPlatform`
- `params`
- `status`
- `startedAt`
- `endedAt`
- `artifactSource`
- `remoteHost`

日志流建议拆成事件：

- `task-started`
- `build-started`
- `build-finished`
- `upload-started`
- `upload-finished`
- `stdout`
- `stderr`
- `cleanup-started`
- `cleanup-finished`
- `task-finished`
- `task-failed`

这样前端既能显示原始日志，也能做结构化阶段提示。

## 12. 自定义工具策略

第一阶段只支持：

- 从内置工具复制为自定义工具
- 在用户工作区生成新的工具清单和资产副本

复制时默认应一并复制：

- 工具清单
- 脚本或资源文件
- 使用说明
- 图标引用
- 导出策略

先不支持：

- 原地修改内置工具
- 图形化自定义工具编辑器
- 在线调试器

## 13. 文档体系

重构时建议同时维护这些文档：

- `docs/DESKTOP_REBUILD_PLAN.md`
- `docs/ARCHITECTURE.md`
- `docs/TOOL_MANIFEST_SPEC.md`
- `docs/REMOTE_EXECUTION.md`
- `docs/EXPORT_PIPELINE.md`
- `docs/CUSTOM_TOOLS.md`
- `docs/DEVELOPMENT_SETUP.md`

要求：

- 每做完一个关键模块，就同步补文档
- 文档写法以“可执行”优先，必须说明入口、依赖、运行方式、调试方式

## 14. 实施顺序

### Phase 0：脚手架

- 创建 Wails 桌面宿主
- 创建 Vue 3 前端骨架
- 建立单仓库模块目录
- 引入基础 UI 栈

### Phase 1：工具规格

- 定义 YAML 工具清单
- 定义 JSON Schema
- 完成清单加载器
- 迁移 1 个 Go 工具和 1 个 Python 工具作为样板

### Phase 2：主路径闭环

- 本地执行打通
- 日志流打通
- SSH 连接打通
- Go 单工具构建缓存打通
- Python 远程脚本执行打通
- 远程清理打通
- 导出打通

### Phase 3：体验补强

- 自定义工具复制
- 连接记忆
- 参数历史
- 更好的错误展示
- 更漂亮的 UI 主题

## 15. 迁移策略

不要直接在现有 `internal/tui` 上继续演化。

建议：

1. 把旧 TUI 视为参考实现，而不是继续生长的主干
2. 先抽离工具本体与平台模型
3. 再建设新的桌面宿主
4. 最后逐个迁移旧工具

## 16. 当前默认结论

如果后续没有新的强约束，按以下默认继续推进：

- 桌面栈：`Wails + Vue 3 + TypeScript + Naive UI + Tailwind CSS + Pinia`
- 清单格式：`YAML + JSON Schema`
- Go 工具：单工具构建产物优先
- Python 工具：脚本源码交付优先
- 远程执行：本地统一调度 + SSH 透传
- 仓库形态：单仓库强模块边界
- 第一阶段目标：只打通主路径
