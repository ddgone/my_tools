## 1. 项目是什么

`my_tools` 已经不再被定义为一个单纯的 TUI 工具箱，而是正在重构为一个**桌面工具平台**。

目标产品不是“把旧界面搬上桌面”，而是做一个以**桌面宿主**为主入口的本地化工具平台，让同一批工具都可以通过统一方式完成：

- 本地执行
- 远程执行
- 导出为独立分发物

当前确定的技术方向是：

- 桌面宿主：`Wails`
- 前端：`Vue 3 + TypeScript`
- UI：`Naive UI + Tailwind CSS`
- 仓库形态：`单仓库 + 强模块边界`

---

## 2. 为什么要重构

原项目基于 `tview`，已经遇到非常明确的上限：

- 复杂交互越来越难做
- 高级能力越来越难扩展
- UI 很难做出真正顺手、现代、漂亮的体验
- 远程执行、导出能力、任务中心、连接管理等功能放在 TUI 里会越来越吃力

所以这次重构的核心判断是：

- **继续堆 TUI 不值得**
- **要把项目升级成桌面工具平台**

这次重构不是美化，而是产品形态升级。

---

## 3. 产品目标

### 3.1 长期目标

做一个真正可用的桌面工具平台，满足下面几类路径：

1. 用户在桌面宿主里选择工具并执行
2. 用户把同一个工具切换为远程执行
3. 用户把同一个工具直接导出成单独分发物
4. 用户未来可以从内置工具复制出自定义工具继续演进

### 3.2 当前阶段目标

当前阶段并不是“把所有东西都做完”，而是先建立一个成立的第一阶段平台。

当前已经确认的阶段目标是：

- 先把桌面宿主做出来
- 先把本地执行真正接通
- 为后续 SSH 远程执行与导出能力留清晰口子

---

## 4. 核心设计原则

这次重构有几个非常关键的设计原则，后面做评估时应该一直围绕它们判断：

### 4.1 能力迁移，不做 UI 原样复刻

不是把旧 `tview` 页面一比一搬过去，而是保留旧项目真正有价值的能力，再用桌面化方式重做交互。

### 4.2 桌面宿主优先

第一性目标是先做出好用的桌面宿主，而不是先把导出能力、打包能力和远程代理一次性全做完。

### 4.3 工具平台，不只是桌面壳

桌面宿主只是入口。真正要建立的是“工具平台”：

- 有统一工具规格
- 有统一执行模型
- 有统一远程执行模型
- 有统一导出模型

### 4.4 同一个工具支持三条路径

同一个工具未来应该自然支持：

- 本地执行
- 远程执行
- 导出分发

### 4.5 Python 工具按脚本交付

Python 工具不优先打成二进制，默认按脚本交付，这样安装目录、远程执行和导出都能复用同一种资产。

### 4.6 内置工具与自定义工具分离

- 内置工具：平台管理资产
- 自定义工具：由用户复制出来单独演进

## 9. 当前版本是怎么实现“从旧 tview 升级过来”的

这是这次重构里最有价值的一点。

当前不是把旧工具重写成一套全新的桌面逻辑，而是：

- 保留旧工具本体
- 捕获旧工具原先挂给 TUI 的执行闭包
- 在 Wails 宿主里直接复用这些执行闭包

这样做的意义是：

- 旧工具能力没有丢
- 新宿主不是空壳
- 可以保留“这确实是从旧版本升级来的”连续性
- 重构速度更快
- 风险更低

```text

```

当前唯一正确的构建方式：

```bash

wails build -clean
```

## 12. 当前阶段适合怎样评估

如果你现在要决定“这个方向还值不值得继续”，建议围绕这几个问题做评估：

### 12.1 架构方向是否正确

你要先判断的不是“页面现在漂不漂亮”，而是：

- Wails 这条路是不是比 `tview` 更对
- 桌面宿主 + 工具平台 的产品定义是不是正确
- 统一工具规格 + 本地/远程/导出 三路径是不是正确

如果这几件事你认同，那说明方向是对的。

### 12.2 当前 UI 方向是否正确

真正需要重新评估的是：

- 当前主页模式是不是你想要的首页形态
- 当前执行页面模式是不是你理想中的主工作区
- “旧版升级感”保留得够不够对
- 当前视觉风格是不是你愿意继续打磨的方向

如果这几件事你不满意，那不代表架构错了，更可能是**产品层和视觉层还需要重新定调**。

### 12.3 当前版本是否已经证明可行性

这一点目前答案是：

- **是，已经证明可行**

因为现在已经明确证明了：

- 桌面宿主可以建立
- 旧工具能力可以迁移进来
- 本地执行可以打通
- 日志与任务模型可以成立

所以现在不再是“能不能做”的问题，而是“该不该沿当前产品形态继续做”的问题。

## 13. 下一步应该做什么

如果继续推进，下一步不应该立刻继续堆 SSH 或导出，而应该先做一个**评估与重新定调阶段**。

推荐顺序如下。

### 13.1 第一步：重新定义界面愿景

先明确：

- 首页到底应该是什么产品叙事
- 执行页到底应该更像 IDE、控制台、工作台，还是专业工具面板
- 如何体现“从旧版升级而来”而不是完全陌生的新壳
- 视觉风格到底走什么方向

### 13.2 第二步：确定新的页面基线

在愿景稳定前，不建议继续大规模叠加功能。

因为一旦页面气质不对，后面接 SSH、导出、自定义工具，只会把错误形态越做越重。

### 13.3 第三步：基线定了之后再继续功能

当页面基线和产品气质确定后，再继续做：

1. SSH 远程执行
2. 工具导出
3. 自定义工具
4. 执行结果入口和参数历史
5. 更完整的任务体系

## 14. 当前建议结论

如果只基于当前状态给一个务实判断，我的建议是：

- **先暂停继续堆功能**
- **先围绕产品愿景和页面形态做一次重新评估**
- **保留当前代码和架构成果，不回退**

原因很简单：

- 架构方向已经证明可行
- 本地执行链已经成立
- 旧能力迁移方式也成立
- 当前真正不满意的是“产品外观与工作流气质”

这说明现在最需要的不是“再写更多功能”，而是“重新定义成品应该长什么样”。
