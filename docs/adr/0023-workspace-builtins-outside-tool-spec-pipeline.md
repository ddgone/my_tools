# ADR 0023: 工作区内置工具独立于工具规格执行链路

## 日期

2026-06-07

## 状态

已采纳

## 背景

项目当前已经形成两条比较稳定的主线：

1. **普通工具主线**：由 `ToolManifest` 驱动，进入本地执行、远程执行、导出和构建缓存链路。
2. **单页工作台主线**：由活动栏、侧边栏和工作区标签页组成，允许在同一窗口内承载多种不同类型的页面。

在引入时间转换、JSON 格式化、Base64 编解码等研发高频小工具时，出现了一个明确分歧：

- 如果继续把它们建模成 Go/Python **工具**，就必须为它们补齐工具规格、执行入口、远程语义、导出语义和构建语义；
- 但这类能力本质上只是桌面宿主内的即时页面能力，既不需要远端环境，也不需要导出产物，更不适合伪装成可分发脚本。

同时，项目已经接受“**能力迁移** 不等于旧交互复刻”和“**单页工作台** 可以承载不止一种页面对象”这两个方向，因此没有必要为了统一而把所有能力都挤进同一条工具执行管线。

## 决策

**把这类研发高频小能力定义为“工作区内置工具”，并让它们独立于 `ToolManifest`、执行、远程和导出链路存在。**

具体约束如下：

1. **入口独立**：工作区内置工具从活动栏中的“内置工具”入口进入，而不是混入普通工具分类树。
2. **标签独立**：打开后在工作区内以独立标签类型渲染，不复用普通工具标签页里的参数区、执行终端和导出区。
3. **实现本地化**：当前默认以前端本地页面实现，不接入 `app/execution.go`、`app/export.go`、`app/internal/builder/`。
4. **能力边界明确**：工作区内置工具当前不承诺远程执行、导出能力、流式日志和长任务模型。
5. **交互保持一致**：虽然不走普通工具链路，但仍要复用同一工作区范式，包括活动栏、左侧搜索面板、右侧标签页和固定标签恢复。

## 放弃的方案

- **方案 A: 继续做成 Go/Python 工具** — 可以复用既有执行链路，但会把大量本不需要的执行、导出和远程语义强加给轻量页面能力。
- **方案 B: 做成宿主设置页里的零散小面板** — 实现简单，但不符合“单页工作台 + 标签页”的主工作区范式，也不利于多工具并行打开。
- **方案 C: 做成新的后端内建工具类型并走统一执行 API** — 抽象上更整齐，但当前收益不足，会在模型层过早引入新的执行形态和额外复杂度。

## 影响

- **正面**：可以快速沉淀一组高频研发工具，而不必等待后端执行链路扩展完成。
- **正面**：不会破坏现有 Go/Python 工具、本地执行、远程执行和导出逻辑。
- **正面**：让单页工作台真正具备“既能承载正式工具，也能承载宿主内建页面能力”的扩展性。
- **代价**：前端需要维护一套路由外的页面注册表、独立标签类型和相应的 UI 组件映射。
- **代价**：普通工具与工作区内置工具之间存在两套能力边界，需要通过术语和文档持续保持清晰。

## 当前适用范围

当前已经适合进入工作区内置工具的能力包括：

- 时间与时区换算
- 文本编解码
- JSON 格式化和校验
- URL / JWT / Query 参数解析
- Hash 摘要和轻量校验

如果某个能力未来明确需要远程环境、长任务、导出产物或脚本分发，再重新评估它是否应提升为普通工具。
